# Step 8 — Documentation: architecture, assumptions, AI-assisted development, prompts, README

Read `AGENTS.md`, `docs/ASSIGNMENT.md` (§6 "AI-Assisted Development" and "Submission
Instructions" are the acceptance criteria of this step), `docs/ASSUMPTIONS.md`, and **every**
report in `prompts/reports/`. Before writing the AI section, ask the developer two questions
and wait: (1) the exact Claude Code version and model name(s) used for the step agents and
the orchestrator; (2) whether the role statement below is accurate or how to change it.

Writing rules: plain, short sentences; no superlatives, no "robust/seamless/leverage"; a
reader should be able to verify every claim in the repository. Nothing about other
solutions or requirements the assignment does not state (the extra-pattern scan runs on this step).

## `docs/ARCHITECTURE.md`

1. Purpose in two sentences.
2. Mermaid diagram of the hexagon: inbound adapter (REST, generated interface) → use cases →
   domain (`TimeDepositCalculator`, plan catalogue, `TimeDeposit`); use cases → repository port
   → persistence adapter (JPA, Flyway, PostgreSQL). Label the dependency direction.
3. Package map (reuse the table from `AGENTS.md`) and the dependency rule, with a pointer to
   `ArchitectureTest`.
4. Request flows: `GET` and `POST`, four or five steps each, including the transaction and the
   row lock.
5. Domain model: why `TimeDeposit`/`TimeDepositCalculator` stayed where they are (assignment
   constraints), the plan catalogue, how a new plan is added (the exact list of files: enum
   constant, catalogue entry, CHECK constraint migration, contract enum, tests — and nothing
   else), how a new rule family would be added (a second field on `Plan`, read by the
   calculator or the use case; no code for it exists today, on purpose).
6. Money: `Double` in the frozen class, `NUMERIC(19,2)` in the database, `BigDecimal` at both
   boundaries, the `new BigDecimal(double)` rounding and why it was kept.
7. Concurrency and idempotency: pessimistic lock, one transaction, `POST` not idempotent;
   what would change for scheduled monthly runs (period tracking) — stated as not built.
8. Deliberately out of scope with one line each: authentication, input validation and error
   responses, pagination, actuator/health, metrics. For each: why (assignment) and the first
   step if it were needed.
9. Verification tooling: characterization tests (frozen), ArchUnit, Testcontainers, Pitest,
   OpenRewrite, Spotless, Spectral, guard rails — one line each with the command.

## `docs/AI-DEVELOPMENT.md` (assignment §6, every bullet answered under its own heading)

- **Tools and setup**: Claude Code (version), model(s) (as the developer states), the Claude
  app for the design session; repository harness: `AGENTS.md`/`CLAUDE.md`, `.claude/rules/`,
  skills (`/verify`, `/commit`, `/review`, `/extend`), hooks (protected files), git hooks,
  `scripts/guardrails.sh`, CI running the same checks. Link each file.
- **Workflow**: design session → written step prompt per step → fresh step agent executes →
  orchestrator verifies independently → fresh review agent → developer reads the diff and
  approves → push. Fix rounds. One paragraph plus a small Mermaid sequence or flow diagram.
- **Reproducibility**: how to run it again — clone, `scripts/setup-hooks.sh`, open Claude Code
  at the root (it loads `CLAUDE.md` → `AGENTS.md` and the rules), use `/verify` and `/extend`;
  the step prompts are in `docs/ai/prompts/`; the environment needs Java 17+, Docker, Node.
- **Custom rules, prompts, configurations**: list with links (rules, skills, hooks, settings,
  prompts).
- **What was AI-assisted and why** — a table: area → generated by agents / written by the
  developer / both → why (speed, breadth of test matrix, boilerplate; versus design
  decisions, requirement readings, review). Be exact: all production code, tests, migrations,
  contract, Dockerfile, workflow and this documentation were generated by agents from the
  prompts and then reviewed; the design, the readings in `ASSUMPTIONS.md`, the prompts' content
  decisions and every approval were the developer's. Role statement to confirm with the
  developer: *"Design decisions, requirement readings and every diff review are mine; code
  and tests were generated by agents under reviewed prompts and automated guard rails."*
- **What the harness caught** — three to five concrete examples taken from the reports
  (e.g. the formatter/JDK pin, the rounding recipe that would have changed behaviour, a
  blocked edit, a Spectral warning). Facts only, with the step they come from.
- **Limits**: hook heuristics, what still needs a human (design gates, reading diffs).
