## Schema (`db/migration/V1__create_time_deposits_and_withdrawals.sql`)

snake_case physical names for the assignment's logical names (A11):

```sql
CREATE TABLE time_deposits (
    id        INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    plan_type VARCHAR(32)   NOT NULL CHECK (plan_type IN ('basic', 'student', 'premium')),
    days      INTEGER       NOT NULL CHECK (days >= 0),
    balance   NUMERIC(19,2) NOT NULL CHECK (balance >= 0)
);
CREATE TABLE withdrawals (
    id              INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    time_deposit_id INTEGER       NOT NULL REFERENCES time_deposits (id) ON DELETE RESTRICT,
    amount          NUMERIC(19,2) NOT NULL CHECK (amount > 0),
    date            DATE          NOT NULL
);
CREATE INDEX withdrawals_time_deposit_id_date_idx ON withdrawals (time_deposit_id, date);
```
Short SQL comments on the *why* only: identity "by default" so seed data may give explicit
ids; `balance >= 0` rather than `> 0` because a deposit may be emptied; the composite index
serves the foreign key lookups (PostgreSQL does not index FK columns automatically) and
date-window queries over a deposit's withdrawals; `plan_type` CHECK mirrors `PlanType` codes
and must be extended when a plan is added (A12); `date` kept as the assignment names it.
If the exact SQL above needs adjusting, adjust — but every constraint listed must exist.

Seed (`db/seed/R__sample_deposits.sql`, repeatable, `INSERT … ON CONFLICT (id) DO NOTHING`):
deposits `(1,'basic',45,10000.00)`, `(2,'student',100,10000.00)`, `(3,'premium',60,10000.00)`,
`(4,'premium',20,10000.00)`; withdrawals `(1,1,500.00,'2026-09-01')`, `(2,1,250.00,'2026-10-01')`,
`(3,3,1000.00,'2026-09-15')`. Then reset both identity sequences past the explicit ids
(`SELECT setval(pg_get_serial_sequence(...), max(id))`), so later inserts do not collide.

## Persistence adapter (`org.ikigaidigital.adapter.out.persistence`)

- `TimeDepositEntity` (`@Entity @Table(name = "time_deposits")`): `Integer id` (`@Id`,
  `GenerationType.IDENTITY`), `PlanType planType` with `@Convert(converter = PlanTypeConverter.class)`
  storing the lowercase code, `int days`, `BigDecimal balance` (`precision = 19, scale = 2`).
  Lombok `@Getter`, `@NoArgsConstructor(access = PROTECTED)`, an all-args constructor;
  no `@Data`, no Lombok equals/hashCode, no setters beyond `balance`.
- `WithdrawalEntity` (`@Table(name = "withdrawals")`): `Integer id`, `int timeDepositId`
  (plain column — **no `@ManyToOne`**; integrity is the database's), `BigDecimal amount`, `LocalDate date`.
- `PlanTypeConverter implements AttributeConverter<PlanType, String>` (`autoApply = false`):
  to DB → `code()`; from DB → `PlanType.fromCode(code).orElseThrow()` (a code outside the
  enum cannot exist thanks to the CHECK; failing loudly is right).
- Spring Data: `TimeDepositJpaRepository extends JpaRepository<TimeDepositEntity, Integer>` with
  `@Lock(LockModeType.PESSIMISTIC_WRITE) @Query("select t from TimeDepositEntity t order by t.id") List<TimeDepositEntity> findAllForUpdate();`
  and `List<TimeDepositEntity> findAllByOrderByIdAsc()`;
  `WithdrawalJpaRepository` with `List<WithdrawalEntity> findAllByOrderByTimeDepositIdAscIdAsc()`.
- `TimeDepositPersistenceAdapter implements TimeDepositRepository` (`@Component`, constructor
  injection): `loadAllForUpdate` → locked entities mapped to `TimeDeposit`; `saveAll` → load
  the entities by id in one query, set `balance` from the domain objects, `saveAll`;
  `loadAllWithWithdrawals` → two queries (deposits, withdrawals) grouped in memory into
  `TimeDepositDetails` — no N+1, no JPA navigation.
- `TimeDepositMapper` (package-private, final, static methods or an injected bean — choose
  one and say why in the report): `BigDecimal` ↔ `Double` with `BigDecimal.valueOf(double).setScale(2, HALF_UP)`
  towards the database and `doubleValue()` towards the domain; `// ASSUMPTION A13` on it.

## Assumptions

- A11 — table/column names: the assignment's camelCase logical names map to snake_case
  physical names (`time_deposits.plan_type`, `withdrawals.time_deposit_id`), PostgreSQL's
  convention; the API keeps the camelCase names. Applied in V1 and the entities.
- A12 — `planType: String (required)` is constrained to the known plan codes by a CHECK
  constraint; adding a plan requires a migration extending it. Applied in V1 / `PlanTypeConverter`.
- A13 — `balance: Decimal` is `NUMERIC(19,2)`; the frozen `TimeDeposit` holds a `Double`, so
  values are converted at the persistence boundary with `BigDecimal.valueOf` and two-decimal
  HALF_UP scale, never with `new BigDecimal(double)`. Applied in the mapper.
- A14 — referential integrity, non-negative balances, positive withdrawal amounts and the FK
  index are enforced by the database, not by application code (assignment: invalid input
  handling not required). Applied in V1.

## Tests (`*IT`, Failsafe, Testcontainers `postgres:17-alpine`)

- `test/.../PostgresContainerSupport` — abstract base with one static `PostgreSQLContainer`
  shared by all ITs (`@ServiceConnection`), started once per JVM.
- `TimeDepositPersistenceAdapterIT` (`@DataJpaTest` + `@AutoConfigureTestDatabase(replace = NONE)`
  + `@Import(adapter, mapper if a bean)`; Flyway runs): context loads with
  `ddl-auto=validate` (mapping matches schema); save/load round trip for the three plan codes;
  decimal fidelity (`0.10`, `123456.78`, `999999999.99`); ordering by id; withdrawals grouped
  under the right deposit and ordered; a deposit without withdrawals has an empty list;
  `loadAllForUpdate` inside a transaction succeeds and returns the same ids; `saveAll`
  persists only `balance`; CHECK violations (`balance < 0`, `amount <= 0`, unknown plan code)
  and the FK violation raise `DataIntegrityViolationException`; the composite index exists
  (`pg_indexes` query).
- `TimeDepositApplicationIT` (`@SpringBootTest`): context loads against the container with
  the two use-case beans present; the `local` profile is **not** active and the tables are
  empty.
- Lock behaviour under concurrency is tested end-to-end in step 5 (two transactions through
  the use case); here only that the locked query runs.
