# Assumptions register

Every reading of an ambiguous requirement gets an id `A<n>` and a row in the table below.
The code where the decision applies carries a `// ASSUMPTION A<n>: <one line>` comment so a reader can trace it back here.

Ids are never reused or renumbered: a decision that changes keeps its id and its row is updated.
`scripts/guardrails.sh` fails when code cites an id that has no row here.

| Id | Requirement text (quoted) | Ambiguity | Decision | Where applied |
|---|---|---|---|---|
| A1 | "The final solution must include **exactly two API endpoints**." | Whether the OpenAPI contract served for Swagger UI, Swagger UI itself or operational endpoints count as endpoints. | The served contract and Swagger UI document the two endpoints and are not endpoints themselves; no actuator or other HTTP surface is added. `/error` is Spring Boot's error handling, not an endpoint, and answers `500` when called directly. | `openapi.yaml`, `TimeDepositsController`, `TimeDepositsApiIT` |
| A2 | "Embrace Hexagonal Architecture." | Whether transaction demarcation, a framework concern, may appear in the application layer. | Transactions are declared with `@Transactional` on use-case services; the domain stays framework-free and the application layer is otherwise free of persistence and web dependencies (enforced by ArchUnit). | `UpdateBalancesService`, `ListTimeDepositsService` |
| A3 | "**Student Plan**: 3% interest (no interest after 1 year)" | Whether "after 1 year" ends on day 365 or day 366, and whether day 365 still earns. | Interest on days 31 to 365 inclusive; none from day 366 (the original's `days < 366`). | `PlanCatalog.standard()` |
| A4 | "**Premium Plan**: 5% interest (interest starts after 45 days)" | Whether day 45 itself earns. | Interest from day 46 (the original's `days > 45`). | `PlanCatalog.standard()` |
| A5 | "No interest is applied for the first 30 days for any existing plans." | Whether the grace period is one global rule or part of each plan, and whether day 30 earns. | Interest from day 31. The grace period is modelled as each plan's earning period rather than a global guard, so each plan states its own first earning day. | `PlanCatalog.standard()` |
| A6 | "Implement logic to calculate monthly interest based on the plan type" | How the stored `planType` string is matched to a plan, and what an unknown or missing code does. | The code is matched exactly and case-sensitively; an unknown, differently-cased or null code earns no interest and raises no error. This is the original behaviour, except that a null code made the original throw `NullPointerException` after day 30, which is invalid input and out of scope. | `PlanType.fromCode` |
| A7 | "Implement logic to calculate monthly interest based on the plan type" | What one call of `updateBalance` represents in time. | One call applies one month of interest, `annualRate / 12`; the method does not advance `days` and does not know the calendar. | `AnnualRate.monthlyInterestOn` |
| A8 | "Create a RESTful API endpoint to update the balances of all time deposits in the database." | What the update endpoint returns, and whether calling it twice is the same as calling it once. | It returns the updated deposits in the same shape as the list endpoint, so the caller sees the effect without a second call. It is not idempotent: each call applies one month of interest, which is why it is a `POST`. | `UpdateBalancesService`, `openapi.yaml`, `TimeDepositsController` |
| A9 | "The GET endpoint should return a list of all time deposits" | In which order deposits and their withdrawals are returned. | Both endpoints return deposits ordered by `id` ascending, each with its withdrawals ordered by `id` ascending. | `TimeDepositRepository.loadAllWithWithdrawals` (port), `TimeDepositDetails` |
| A10 | "Create a RESTful API endpoint to update the balances of all time deposits in the database." | What happens when two balance updates run at the same time. | Concurrent updates are serialised by locking the deposit rows until the transaction ends, so none loses an interest application. No idempotency key or period tracking is added: the assignment's schema has no field for it and `updateBalance` has no notion of time. | `UpdateBalancesService`, `TimeDepositRepository.loadAllForUpdate` |
| A11 | "Define the following tables: `timeDeposits` [...] `withdrawals` [...] `timeDepositId`" | Whether the camelCase names are physical table and column names. | They are logical names. The schema uses PostgreSQL's snake_case convention (`time_deposits.plan_type`, `withdrawals.time_deposit_id`); the API keeps the camelCase names. | `V1__create_time_deposits_and_withdrawals.sql`, `TimeDepositEntity` |
| A12 | "`planType`: String (required)" | Whether any string is a valid plan type in the database. | A CHECK constraint limits `plan_type` to the known plan codes; adding a plan requires a migration that extends it. | `V1__create_time_deposits_and_withdrawals.sql`, `PlanTypeConverter` |
| A13 | "`balance`: Decimal (required)" | Which decimal type stores the balance, and how the frozen `TimeDeposit`'s `Double` balance crosses into it. | `NUMERIC(19,2)`. The adapter converts with `BigDecimal.valueOf(double)` and a two-decimal `HALF_UP` scale, never with `new BigDecimal(double)`, and back with `doubleValue()`. | `TimeDepositMapper`, `TimeDepositResponseMapper` |
| A14 | "Handling invalid input or exceptions is not required." | Where the integrity of stored data is enforced. | The database enforces it: the foreign key from `withdrawals` to `time_deposits`, non-negative `days` and `balance`, positive withdrawal `amount`, and an index on the foreign key column. Application code adds no validation. | `V1__create_time_deposits_and_withdrawals.sql`, `WithdrawalEntity` |
| A15 | "`withdrawals`" in the GET schema; "`timeDepositId`: Integer (foreign key, required)" | Whether each withdrawal nested in a deposit repeats `timeDepositId`. | It does not: a nested withdrawal has `id`, `amount` and `date`; its deposit is the enclosing object. | `openapi.yaml` (`Withdrawal`) |
| A16 | "`balance`: Decimal (required)" | How money is typed in the contract. | `type: number` with no `format`, so the generator produces `BigDecimal` and no `float`/`double` rounding reaches the JSON. | `openapi.yaml` (`balance`, `amount`) |
| A17 | "Create a RESTful API endpoint to update the balances of all time deposits" | Which REST resource and method model a non-idempotent update of the whole collection. | `POST /time-deposits/update-balances`, a controller resource: `PUT` would promise idempotency, and a noun such as `/balance-updates` would name a resource that can never be retrieved. | `openapi.yaml` |
| A18 | "Create a RESTful API endpoint [...]" | Whether and how the API is versioned. | Paths start with `/api/v1`; a breaking change would add `/api/v2` beside it. | `openapi.yaml` |
| A19 | "Create a RESTful API endpoint to retrieve all time deposits." (the assignment names no users, roles or security) | Whether the endpoints require authentication. | No authentication: out of scope for the kata. In production a bearer token would be checked at the gateway or by Spring Security as a resource server. | `openapi.yaml` |
| A20 | "Provide clear instructions on how to trigger the endpoints using the Swagger contract." | Whether Swagger UI shows the hand-written contract or one introspected from the code. | Swagger UI is a static page that renders `openapi.yaml`, served unchanged at `/openapi.yaml`, with three assets unpacked from the `swagger-ui` webjar at build time (CSS, bundle, preset). springdoc is not used, because its UI cannot run without introspecting the code, and the webjar's own demo and OAuth pages are never served. | `application.yml`, `WebConfiguration`, `static/swagger-ui/index.html`, `pom.xml` |
