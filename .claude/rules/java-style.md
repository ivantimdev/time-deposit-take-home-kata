# Java style rules

- Formatting is google-java-format via Spotless; run `./mvnw spotless:apply` before every commit.
- Names reveal intent and reuse the README's domain words (`planType`, `days`, `balance`, `withdrawals`).
- No abbreviations (`xs`, `a2d`, `tmp`, `res`) and no `Impl`, `Helper`, `Util(s)` or `Manager` suffixes.
- Adapters are named by role or technology (`TimeDepositPersistenceAdapter`, `TimeDepositsController`).
- Comments say *why* or cite an assumption id; they never narrate *what* the code does.
- No Javadoc on self-explanatory members.
- No commented-out code, no `TODO`/`FIXME`, no `@author`, no "generated by" banners, no `System.out`.
- Prefer records for values, immutable fields, and `final` locals where it aids reading.
- Keep classes small with one reason to change (SOLID); prefer composition over inheritance.
- Use `Optional` only as a return type.
- Lombok only in `adapter.*` and `config`, for boilerplate a reader would skip anyway (`@RequiredArgsConstructor`, `@Getter`, JPA's `@NoArgsConstructor`).
- Never `@Data`, never Lombok-generated equals/hashCode on JPA entities, never Lombok in `domain`/`application` (records and plain classes there).
- No MapStruct: mapping is explicit and tested.
- Money crosses boundaries as `BigDecimal` (scale 2); the frozen `Double` in `TimeDeposit` is converted with `BigDecimal.valueOf` at the adapter boundary only.
- Delete code the moment it is unused. A `rewrite:dryRun` with findings fails `/verify`.
